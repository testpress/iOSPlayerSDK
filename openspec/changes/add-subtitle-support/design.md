## Context

The SDK currently has no subtitle/caption support. The `TPStreamPlayerConfiguration` struct has an unused `enableCaptions` flag, but no model, no parsing, no UI, and no rendering.

The existing **notice view** pattern in `TPStreamPlayerViewController` is the closest analogue — a UIView added as a subview of `containerView`, frame-based sizing in `viewDidLayoutSubviews`, programmatically created, and moved with the container during fullscreen transitions. SubtitleView follows the same pattern.

The player architecture is:
- `TPAVPlayer` (AVPlayer subclass) — asset fetching, DRM, quality selection
- `TPStreamPlayer` (NSObject wrapper) — KVO-based state observation, @objc dynamic `currentTime` updated every 0.5s via periodic time observer
- `TPStreamPlayerViewController` (UIKit) / `TPStreamPlayerView` (SwiftUI) — presentation layers

The API backend (both StreamsAPI and TestpressAPI) returns subtitle tracks inside the `video` object as a `tracks` array with `type: "Subtitle"`, `language`, `url`, `name`, and `subtitle_type` fields.

## Goals / Non-Goals

**Goals:**
- Parse subtitle track metadata from both StreamsAPI and TestpressAPI responses
- Download WebVTT files and render subtitles in sync with playback
- Provide language selection UI in both UIKit and SwiftUI settings menus
- Support configuration via `enableCaptions` (show UI) and `autoSelectFirstSubtitle` (auto-select first track on player ready)
- All subtitle logic self-contained within SubtitleView (download, parse, render)
- Reuse existing 0.5s `currentTime` periodic observer — VC pushes time to SubtitleView

**Non-Goals:**
- No native HLS `AVMediaSelectionGroup` subtitle handling — backend always delivers sidecar URLs
- No external public API for subtitle control — all interaction through settings UI and config flags
- No caching of parsed WebVTT between track switches (redownload on each switch)
- No advanced VTT features (regions, styles, positioning — text-only rendering)
- No SRT or other non-VTT subtitle format support — backend only delivers WebVTT

## Decisions

### 1. Self-contained SubtitleView (not a separate SubtitleManager)
**Decision**: The SubtitleView owns the full lifecycle: download WebVTT via `URLSession`, parse with SwiftSubtitles, look up cues by time, and render to its UILabel.

**Rationale**: WebVTT download + parse + lookup is ~30 lines of logic. Keeping it in the view avoids the indirection of a separate manager class. If caching, multi-track preloading, or offline support is needed later, a manager can be extracted without changing the view interface.

### 2. VC pushes time updates to SubtitleView
**Decision**: SubtitleView does NOT observe time directly. Instead, it exposes an `updateSubtitle(at time: TimeInterval)` method. The VC (UIKit) or TPStreamPlayerObservable (SwiftUI) calls this method every time `currentTime` changes.

**Rationale**: The 0.5s time update already flows through the system. The VC already has access to `TPStreamPlayer.currentTime`. Having the VC push time to SubtitleView avoids a separate KVO subscription in the view — no setup, no teardown, no deinit concerns. SwiftUI already has `observedCurrentTime` via `@Published`, so the SwiftUI subtitle view reads it directly.

### 3. No public API for subtitle control
**Decision**: No methods exposed on TPStreamPlayer or TPAVPlayer for subtitle manipulation. All control is through the settings UI and config flags.

**Rationale**: Subtitle management is entirely self-contained within the SubtitleView. The settings menu reads tracks from `player.asset?.video?.tracks` and sets the active track on the subtitle view directly. Consumers only configure via `enableCaptions`/`autoSelectFirstSubtitle`.

### 4. SwiftSubtitles (dagronf/SwiftSubtitles) for WebVTT parsing
**Decision**: Use the `Subtitles(content:expectedExtension:)` API with `.vtt` extension.

**Rationale**: Already supports iOS 12+ (matching SDK target), MIT license, handles WebVTT parsing including edge cases (BOM, cue timings, multi-line text). Available via both SPM and CocoaPods. The VTT coder is well-tested.

**Alternatives considered**: Inline WebVTT parser — possible but adds maintenance burden for no clear benefit.

### 5. UIKit + SwiftUI parity with separate implementations
**Decision**: UIKit uses a UIView-based SubtitleView; SwiftUI uses its own subtitle view in the ZStack.

**Rationale**: Matches the existing pattern of dual UI framework support. The UIKit subtitle view is managed by the VC's `viewDidLayoutSubviews`; SwiftUI subtitle view is part of `TPStreamPlayerView`'s ZStack.

## Risks / Trade-offs

| Risk | Mitigation |
|---|---|
| **Large WebVTT files** could delay initial subtitle display | Download is async; subtitles appear once download completes. For typical sidecar files (<100KB), this is ~instant |
| **Auto-generated captions** may have poor quality timing | The `isAutoGenerated` flag is preserved in SubtitleTrack for potential UI differentiation, but rendering is identical |
| **SwiftSubtitles dependency version drift** | Pin to a specific major version |
